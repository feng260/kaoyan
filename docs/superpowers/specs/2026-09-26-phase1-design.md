# 研钟 Phase 1 产品化设计

## 1. 目标

在 Phase 0 已完成服务端规则计划、Android onboarding、active plan 查询和个人学习档案的基础上，完成 Phase 1 的产品化闭环：

1. 规则计划使用稳定、可维护的模板生成。
2. 服务端 active plan 能幂等落地为 Android 本地可执行任务。
3. 首页直接展示并使用当天计划节奏。
4. 基于本地有效专注记录生成离线规则周报。

本阶段不实现 AI 计划、AI 周报、动态重排、付费和分享能力。

## 2. 设计原则

- **服务端计划权威**：阶段、日期、标题、科目和计划时长以服务端计划为准。
- **本地任务可执行**：Android 将计划项转换为本地任务，复用现有任务、首页和专注流程。
- **本地优先降级**：同步失败不阻塞使用，不删除已有本地任务；没有服务端计划时继续使用现有本地计划。
- **幂等同步**：同一个服务端计划项重复同步不会生成重复任务或重复科目。
- **边界分离**：服务端计划数据不直接并入现有 clientGuid 墓碑同步协议，避免破坏多设备同步。
- **有效会话统一口径**：周报只统计 `valid = true` 的专注 session，与学习档案和统计页一致。

## 3. 范围

### 3.1 规则计划模板

保留现有 `Plan`、`PlanStage`、`PlanItem` 数据模型和 `/plans/generate` 接口。在现有纯函数生成器上整理模板边界：

- 阶段模板：基础阶段、强化阶段、冲刺阶段。
- 科目任务模板：按薄弱科目轮转生成学习任务。
- 复盘模板：每日预算达到阈值时生成复盘任务。
- 任务标题、优先级、阶段归属和每日预算继续由规则生成器确定。
- 同样输入必须产生稳定输出。

不增加 AI 字段以外的新计划来源，不改变现有计划校验规则。

### 3.2 服务端计划落地到 Android

Android 拉取 `PlanDto` 后，通过独立的计划同步器将计划项转换为本地任务：

- 计划项的服务端 `plan.id` 与 `item.id` 作为外部来源标识。
- 同步器先识别当前计划版本，再按计划项执行新增或更新。
- 同一计划重复刷新不会重复创建本地任务。
- 新计划生成后新增对应任务，旧计划任务不覆盖用户已有本地任务。
- 计划项状态变化只更新由该计划项创建的本地任务，不修改用户手工创建的任务。
- 服务端科目名称与本地科目按名称匹配；不存在时创建来源于计划的本地科目。
- 服务器不可用、计划为空或同步失败时，保留本地任务并继续使用现有兜底逻辑。

计划来源元数据必须能够区分“服务端计划任务”和“用户本地任务”。优先复用现有任务扩展字段；若现有结构没有合适字段，则增加最小字段，不改变旧任务的默认行为。

### 3.3 首页今日节奏

首页今日区域按以下优先级取数：

1. 当前日期存在已同步的服务端计划任务时，展示计划阶段、计划时长、任务列表和完成进度。
2. 没有服务端计划任务时，展示现有本地任务和 468 天计划逻辑。
3. 计划加载或同步失败时，继续展示本地内容，并提供非阻塞状态提示。

每项计划任务应能进入现有专注流程。首页不得复制计划生成逻辑，也不得直接访问数据库；由 ViewModel 或 Repository 提供已经筛选好的今日状态。

今日节奏至少展示：

- 当前阶段名称。
- 今日计划总分钟数。
- 已完成分钟数或完成项数。
- 剩余任务。
- 任务标题、科目、计划时长和完成状态。

### 3.4 规则版周报

周报以本地自然周为范围，默认使用系统时区和周一至周日边界，基于本地有效 session、任务和科目生成：

- 本周有效专注时长。
- 活跃天数。
- 完成任务数。
- 周目标完成率；没有周目标时显示未设置，不伪造百分比。
- 科目投入排序。
- 峰值时段。
- 每日专注趋势，缺失日期补零。
- 空数据状态和没有科目状态。

周报聚合放在纯 Kotlin 数据层，页面只渲染不可变状态。周报可以接入现有统计页，优先复用现有导航和统计页面，不新增深层导航。

## 4. 数据流

```text
服务端规则计划
    ↓ GET /plans/active
Android PlanViewModel
    ↓
计划同步器
    ↓ 幂等转换
本地 subjects / tasks
    ↓
首页今日节奏 ──→ 现有专注流程 ──→ 有效 session
                                      ↓
                              学习档案 / 规则周报
```

服务端计划继续是服务端权威数据；本地任务是 Android 的执行投影。服务端计划同步不进入通用多设备墓碑同步协议。

## 5. 模块边界

### 服务端

- `planning/generator.ts`：阶段、科目和复盘模板生成。
- `planning/service.ts`：计划持久化、版本和 active plan 查询。
- `planning/routes.ts`：维持现有鉴权、限流和响应协议。
- 服务端测试继续覆盖生成器、校验、事务、用户隔离和计划历史。

### Android 数据层

- 计划 DTO 继续位于 remote 层。
- 新增独立计划落地/同步组件，负责 DTO 到本地任务的转换和幂等。
- Repository 负责本地事务和查询，不让 Composable 直接访问数据库。
- 现有本地任务和同步协议保持兼容。

### Android 界面层

- `PlanViewModel` 负责 active plan 加载、同步状态和今日计划状态。
- 首页 ViewModel 消费今日任务状态，不重复实现筛选和统计。
- `MineScreen` 保留当前 Phase 0 学习档案改造。
- 规则周报复用现有统计入口和主题组件。

## 6. 错误处理与降级

- active plan 请求失败：标记服务端计划不可用，继续使用本地任务。
- 单个计划项数据异常：跳过该项并记录同步结果，不影响其他本地任务。
- 科目创建失败：保留任务同步失败状态，不删除已有数据。
- 重复同步：按来源计划 ID 和计划项 ID 去重。
- 计划重新生成：新计划任务与旧计划任务分开管理，不覆盖手工任务。
- 周报没有 session：显示空状态，所有数值使用零或“暂无”。
- Android 进程重启后：同步标识和已落地任务状态从本地持久化数据恢复，不依赖内存缓存。

## 7. 测试策略

### 服务端

- 模板生成的阶段连续性、每日预算、项目上限和稳定输出。
- 计划重新生成后的版本、归档和历史保留。
- 现有 `npm run verify` 必须继续通过。

### Android 数据层

- 相同计划重复同步不重复创建任务。
- 相同科目名称不重复创建科目。
- 新计划不覆盖用户手工任务。
- 计划日期过滤只产生当天任务。
- 计划状态和完成状态转换符合预期。
- 网络失败不清空本地任务。
- 周报覆盖空数据、跨周边界、缺失日期补零、无效 session、科目排序、峰值时段和目标完成率。

### 构建与验收

- Android `testDebugUnitTest` 通过。
- Android Debug APK 构建成功。
- 服务端 `npm run verify` 通过。
- 真机或模拟器验证：登录、档案、计划同步、首页今日节奏、专注启动和周报展示。

## 8. 非目标

本阶段明确不做：

- AI 计划生成和 AI 周报。
- 动态重排和实时自适应计划。
- 计划分享、成就体系、邀请码和 Web 仪表盘。
- 将服务端计划强行并入现有通用同步墓碑表。
- 重写计时器、session 统计或现有云同步协议。

## 9. 完成定义

Phase 1 只有在以下条件全部满足时才视为完成：

1. 规则模板生成可测试、可重复，并通过服务端验证。
2. Android active plan 能幂等落地为本地任务和必要科目。
3. 首页能够展示并启动当天服务端计划任务。
4. 无网络时首页和专注功能继续可用。
5. 规则周报能基于有效 session 离线生成并正确处理空状态。
6. Android 单测、服务端验证和 Debug 构建均通过。
7. 现有 Phase 0 的登录、同步、数据导出、注销和 MineScreen 功能不回归。
